**Goal:** Stop `getHeaderState` awaiting `sweepStaleJobs` inline on every page view; schedule it with `after()` so the header's response no longer pays for a write-shaped Turso round trip that usually finds nothing.

## Ruling: do NOT reuse `sweepStudioForUser`

The controller brief said "reuse that helper if it already covers this scope rather than duplicating". It does not cover this scope. `sweepStudioForUser(userId)` runs **two** sweeps — `sweepStaleJobs` **and** `sweepIdleConversations` (the 3-day idle-conversation archive from #181). Calling it from the header would make every page view on the whole site trigger conversation archiving, which today only happens on a `/studio` load or the daily cron. That is a change to when user-visible state mutates — i.e. sweep semantics, which this plan's Global Constraints put out of scope.

So: a module-local, non-exported never-reject wrapper lives in `src/components/site-header-actions.ts`, structurally mirroring `sweepStudioForUser`'s try/catch/log but sweeping jobs only. `"use server"` requires every **exported** binding to be an async function; a non-exported async helper is fine (the file already has one, `runningJobsForCurrentUser`).

Cost if this ruling is wrong: a small amount of duplicated try/catch shape (~8 lines) that a future third caller would want factored into `src/lib/generation-job.ts`. Cheap to undo. The opposite mistake — silently moving idle-archiving onto every page view — is a behavior change nobody asked for and would be hard to notice.

## Ruling: accepted one-view staleness in the badge

Before this change, an overdue job was transitioned to `failed` *before* `countActiveGenerationsForUser` ran, so it could never be counted. After it, the count can include a job that is past `STALE_JOB_MS` but not yet swept, so the header badge can read one too high for exactly one header fetch. It self-corrects on the next header fetch — which the header already performs on every `pathname` change (`src/components/site-header.tsx:39-52`), not just on first mount — and on the next `/studio` load, `/design` thread open, or the daily cron.

This is the identical trade #212 accepted for the Studio lanes, and it is what "keep the running-jobs badge read inline" in the issue implies. It must be stated in the code, in the docblock on `runningJobsForCurrentUser`, so a future reader does not "fix" it by re-awaiting.

Cost if this ruling is wrong: a badge that says "1 generating" for one navigation when the generation actually timed out. No money, no data, no fulfillment path touched.

- [ ] **Step 1: Add the `after` mock to the test file's mock block**

The existing test file has no `next/server` mock. Add one in the same style as `src/app/studio/__tests__/studio-archive.integration.test.ts` — a `vi.hoisted` queue plus a drain helper — so a test can assert "scheduled but not yet run" and then run it.

Insert this immediately after the existing `vi.mock("@/lib/generation-job", ...)` block (which ends at the line `}));` before `const { getHeaderState } = await import(...)`), in `src/components/__tests__/site-header-actions.test.ts`:

```ts
/**
 * `after()` is scheduled, not awaited (#210): the sweep must not be on the
 * response path. Same mocking shape as the Studio's after()-sweep tests
 * (src/app/studio/__tests__/studio-archive.integration.test.ts) — queue the
 * callbacks so a test can assert both that nothing ran during the request
 * and what happens when the runtime later drains them.
 */
const afterQueue = vi.hoisted(() => ({ callbacks: [] as (() => unknown)[] }));

vi.mock("next/server", () => ({
  after: (cb: () => unknown) => {
    afterQueue.callbacks.push(cb);
  },
}));

/** Run every queued `after()` continuation, in registration order. */
async function drainAfter() {
  while (afterQueue.callbacks.length) {
    await afterQueue.callbacks.shift()!();
  }
}
```

Then add `afterQueue.callbacks.length = 0;` as the last line inside the existing `beforeEach(() => { ... })` block.

```ts
/**
 * The header's lazy stale-job sweep, in a shape `after()` can safely run:
 * it never rejects. An unhandled rejection out of an `after` continuation
 * runs on the shared Fluid instance, not inside anyone's request, and can
 * take other users' work down with it — the same reason
 * `after(() => runGenerationJob(...))` in design/actions.ts never throws
 * past its boundary.
 *
 * Deliberately NOT `sweepStudioForUser` (src/lib/studio.ts), even though it
 * takes the same `{ scope: "user" }` shape: that helper also runs
 * `sweepIdleConversations`, so reusing it here would move the 3-day
 * conversation archive onto every page view of every route, which is a
 * behavior change, not a latency fix.
 */
async function sweepUserJobsAfterResponse(userId: string): Promise<void> {
  try {
    await sweepStaleJobs({ scope: "user", userId });
  } catch (err) {
    console.error(
      "[header] sweepStaleJobs failed",
      err instanceof Error ? err.message : String(err)
    );
  }
}
```
