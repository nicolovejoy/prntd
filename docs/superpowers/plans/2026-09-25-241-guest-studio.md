# #241 — guests in Studio (plan)

Slice A of the 2026-09-25 batch (`docs/superpowers/plans/2026-09-25-batch.md`).
Issue #241, option 1 (decided by Nico 2026-09-25): open the Studio bench and
Library to guests, add a "Sign up to keep these designs" line, point the cart
CTAs back to `/studio` (reverses ruling W1 from PR #219).

## What is true today

- `/studio` and `/studio/library` call `requireRealUser`, which redirects both
  signed-out visitors AND anonymous (guest-funnel) sessions to `/sign-in`.
- Middleware only checks for a session cookie. An anonymous session has one,
  so a guest already passes middleware on `/studio`; `requireRealUser` is what
  bounces them. A first-time visitor with no cookie is bounced by middleware.
- Three Studio server actions refuse anonymous sessions outright:
  `getStudioLanes` (the bench poll), `deleteConversations` (bench bulk delete)
  and `deleteImages` (library bulk delete). A guest let into the pages without
  changing these would see the bench but every poll would throw, and select
  mode would fail on both views.
- Every other action reachable from the bench, library and image detail page
  already accepts any session and enforces ownership by user id:
  `generateDesign`, `closeConversation`, `cancelGeneration`, `deleteDesign`,
  `openConversation`, `setPrimaryImage`, `getConversationImages`. Publish is
  refused for guests (`publishImage`'s `isAnonymousUser` check, #214) and the
  image detail page shows "Sign in to publish" instead of the button.
- Lane and image queries are user-id scoped (`getStudioLanesData(userId)`,
  `getUserImageLibrary(userId)`), so a guest sees exactly their own work.

## Rulings made while planning

R1. **Gate predicate.** A new `canUseStudio(user, guestFunnel)`: no user →
false; a real user → true; an anonymous user → true only when
`GUEST_FUNNEL_ENABLED` is on. With the flag off, Studio behaves exactly as
today (guests bounce to sign-in, the actions refuse them). The pages and the
three actions share this one predicate so they cannot disagree.

R2. **Cookie-less first visit still goes to sign-in.** Middleware is
unchanged; `/studio` stays in `ALWAYS_PROTECTED`. Only its comment changes.

R3. **The line lives in the pages, not the Studio layout.** Layouts do not
re-render on navigation and Next's auth guide warns against session-dependent
rendering there. Each page already reads the session through the gate, so the
gate returns `isGuest` and each page renders the same `GuestKeepLine`.

R4. **`requireRealUser` stays** for `/orders` (brief: `/orders` stays behind
`requireRealUser`).

R5. **The header running-jobs badge stays off for guests.** Not in #241's
scope; the badge's docblock rationale is rewritten so it stays accurate now
that guests can reach `/studio`. Flagged as a follow-up.

R6. **W1 reversal, including its one cost.** Both cart CTAs go to `/studio`.
A visitor with no session at all who opens an empty `/cart` and taps "Start a
design" now lands on sign-in (R2) instead of `/design`. Anyone with a cart
line has a session, so "Add another design" always reaches the bench. This is
the decision as written; recorded, not worked around.

## Tasks

### Task 1 — Studio access gate (`src/lib/require-user.ts`)

Add:

- `canUseStudio(user, guestFunnel: boolean): boolean` (pure).
- `requireStudioUser(): Promise<{ session; isGuest: boolean }>` — page gate;
  `redirect("/sign-in")` when `canUseStudio` is false.
- `requireStudioActionSession()` — action gate; throws `Error("Unauthorized")`
  when `canUseStudio` is false, returns the session otherwise.

Acceptance:
- signed-out → redirect / throw;
- anonymous + flag on → allowed, `isGuest: true`;
- anonymous + flag off → redirect / throw;
- real user → allowed, `isGuest: false`, whatever the flag.

Tests: `src/lib/__tests__/require-user.test.ts` gains cases for both new
functions and the pure predicate across the flag.

### Task 2 — Pages and actions on the new gate

- `/studio` and `/studio/library` call `requireStudioUser`.
- `getStudioLanes`, `deleteConversations` (`src/app/studio/actions.ts`) and
  `deleteImages` (`src/app/designs/actions.ts`) call
  `requireStudioActionSession`; docblocks that call the Studio
  "personal-record, guests refused" are rewritten.

Acceptance:
- a guest (flag on) polls and gets only their own lanes;
- a guest (flag off) is refused by all three actions;
- a guest's bulk delete deletes their own conversations/images and reports
  another user's ids as `not_found` / `not-owned`, touching nothing.

Tests: update `studio-actions.integration.test.ts`,
`delete-conversations.integration.test.ts`, and add guest cases to
`delete-images.integration.test.ts` (real in-memory libSQL; flag set via
`process.env.GUEST_FUNNEL_ENABLED` per test and restored).
