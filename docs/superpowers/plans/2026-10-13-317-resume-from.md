# Resumed checkout keeps its way back (#317 item 4, with item 6): implementation plan

> Built subagent-driven on 2026-10-13 while Nico was away: one Sonnet implementer for the slice in its own worktree, the controller re-runs the CI gate, one Opus whole-branch review, a dispatched real-Stripe e2e as the smoke. The ledger with every ruling is `docs/superpowers/ledgers/2026-10-13-317-resume-from.md`.

**Goal:** when Stripe sends a buyer to `/order/confirm` without a completed payment and the page offers "Return to checkout", the resumed `/checkout` page's Back link goes where the original one went (the cart, or the image detail page), not to the Shop. On the way, `safeCheckoutReturnPath` stops accepting the three dot-segment shapes the repo's `safeNextPath` already rejects.

**Source of the work:** https://github.com/nicolovejoy/prntd/issues/317. Item 4 is agreed by Nico (comment of 2026-10-11: "carry `from` on Stripe's `return_url` and pass it through `safeCheckoutReturnPath` is agreed: build it"). Item 6 is a finding of the #314 adversarial review with a named fix (reuse `safeNextPath`); it touches the same function this slice relies on, so it is built here. Items 1, 2, 3, 5 and 7 are not in this slice.

**Architecture:** the two Stripe session builders in `src/lib/checkout.ts` take an optional `returnPath`; for an embedded session they append `&from=<encoded safe path>` to `return_url`. The two embedded callers pass the back path they already hold. `/order/confirm` reads `from` back from its own URL and builds the resume link with `embeddedCheckoutPath`, the one builder every `/checkout` link already goes through, so the same sanitiser runs on the way out and on the way back. No schema change. No new user-facing string.

**Branch and worktree:** `claude/317-resume-from` at `.claude/worktrees/317-resume-from`, off `origin/main` at `a59e3c2`.

## Task 1: `safeCheckoutReturnPath` resolves dot segments and caps length (item 6)

### Files

- `src/lib/embedded-checkout.ts`
- `src/lib/__tests__/embedded-checkout.test.ts`

### The problem

`safeCheckoutReturnPath` (`src/lib/embedded-checkout.ts:113`) checks the raw string: starts with one `/`, no `//` prefix, no backslash, no control character. A browser resolves dot segments before it looks at the leading slashes, so `/.//evil.example`, `/..//evil.example` and `/cart/..//evil.example` all pass and all mean `//evil.example`. The repo already has `safeNextPath` in `src/lib/safe-next.ts`, which resolves the value against a dummy origin and rejects a resolved pathname that starts with `//`. There is also no length cap.

### The change

Keep the four existing raw checks (they keep the existing tests true and reject a control character outright instead of letting the URL parser strip it). Then:

1. Reject a `from` longer than `MAX_CHECKOUT_RETURN_PATH_LENGTH = 2048` characters (a new exported constant with a one-line comment: the value travels inside Stripe's `return_url` and the sign-in `next=`, both of which have URL length limits of their own). Fallback `/shop`.
2. Return `safeNextPath(from, "/shop")` (import from `@/lib/safe-next`). It returns the resolved `pathname + search + hash`, so a path with a dot segment comes back resolved (`/cart/./x` → `/cart/x`) and the three shapes above fall back to `/shop`.

Update the doc comment: it now says the value is resolved the way a browser would resolve it before the origin check, and names `safeNextPath` as the shared rule.

### Tests (add to the `safeCheckoutReturnPath` describe)

- `/.//evil.example`, `/..//evil.example`, `/cart/..//evil.example` each → `/shop`.
- `/cart/./x` → `/cart/x` (resolved, accepted).
- `/d/img-1?front=a&back=b&size=M&swap=1` → unchanged.
- A string of 2049 characters starting with `/d/` → `/shop`; the same shape at 2048 → accepted unchanged.
- The existing tests must keep passing unchanged.

Run `src/lib/__tests__/embedded-checkout.test.ts` and `src/app/checkout/__tests__/page.test.tsx` (its `from` cases go through this function).

## Task 2: an embedded session's `return_url` carries `from` (item 4, outbound half)

### Files

- `src/lib/checkout.ts`

- `src/app/d/__tests__/buy-published-design-embedded.integration.test.ts`
- `src/app/cart/__tests__/checkout-cart-embedded.integration.test.ts`

### The change

Both builders in `src/lib/checkout.ts` (`buildCheckoutSessionParams` at line 33 and `buildCartCheckoutSessionParams` at line 126) take a new optional parameter:

```ts
/**
 * Embedded only: the same-origin path /checkout's Back link goes to. It is
 * appended to `return_url` as `from=`, so when Stripe sends the buyer to
 * /order/confirm without a completed payment the "Return to checkout" link
 * there can hand it back to /checkout (#317). Run through
 * `safeCheckoutReturnPath` here, the point where it leaves our control.
 * Ignored for a hosted session, whose way back is `cancelUrl`.
 */
returnPath?: string;
```

For an embedded session:

```ts
return_url: `${params.appUrl}/order/confirm?session_id={CHECKOUT_SESSION_ID}${
  params.returnPath === undefined
    ? ""
    : `&from=${encodeURIComponent(safeCheckoutReturnPath(params.returnPath))}`
}`,
```

`{CHECKOUT_SESSION_ID}` stays the literal Stripe placeholder; it is Stripe that substitutes it. Hosted output does not change at all. `safeCheckoutReturnPath` is imported from `@/lib/embedded-checkout` (that module imports nothing from `checkout.ts`, so there is no cycle; check before you import).

Callers:

- `createStripeCheckoutForOrder` (`src/lib/order-checkout.ts`, the `buildCheckoutSessionParams` call near line 143): add `returnPath: params.embedded?.backPath` (undefined when hosted). Update the `embedded` doc comment (line 80 onward): `backPath` is also what `return_url` carries as `from`.
- `checkoutCart` (`src/app/cart/actions.ts`, the `buildCartCheckoutSessionParams` call before line 760): add `returnPath: embedded.enabled ? CART_PATH : undefined`. Update the comment near line 586 that describes the `url` shape, and any comment there that says the way back after a Stripe return is the Shop.

### Tests

`src/lib/__tests__/checkout.test.ts`, for each builder:

- embedded with `returnPath: "/d/img-1?size=M"` → `return_url` is exactly `https://prntd.org/order/confirm?session_id={CHECKOUT_SESSION_ID}&from=%2Fd%2Fimg-1%3Fsize%3DM` (use the file's existing `appUrl`).
- embedded with `returnPath: "//evil.example"` → `&from=%2Fshop`.
- embedded without `returnPath` → `return_url` unchanged from today (the existing tests at lines 66 to 80 and 296 to 330 already cover this; keep them).
- hosted with `returnPath: "/cart"` → `success_url` and `cancel_url` exactly as today and no `return_url`.

`src/app/d/__tests__/buy-published-design-embedded.integration.test.ts`: the three `return_url` assertions (lines 216, 324, 340) now end in `&from=` followed by the percent-encoded return path the action passed as `backPath` (the test already imports `buyPageHref`; build the expected value from it rather than hard-coding the picks).

### The change

`resolveConfirmView` (`src/lib/checkout-session-status.ts:99`) gets one more optional field, `from?: string`, and builds the embedded resume link with the shared builder:

```ts
const resumeHref =
  stripeState.uiMode === "embedded" && params.embeddedEnabled
    ? embeddedCheckoutPath(params.sessionId, params.from ?? "")
    : stripeState.url ?? null;
```

`embeddedCheckoutPath` (import from `@/lib/embedded-checkout`) runs `safeCheckoutReturnPath`, so a missing, unsafe or over-long `from` becomes `from=%2Fshop`, which is the Back link the resumed page shows today. The doc comments of the type and the function say where `from` comes from (Stripe's `return_url`, written by Task 2) and that it is sanitised again here because it arrives in the query string.

`src/app/order/confirm/page.tsx`: read `from` from `searchParams` the way the page reads `session_id` (a string, else undefined) and pass it to `resolveConfirmView`. `src/app/checkout/page.tsx`: the header comment says a cart session arrives with `from=/cart`; add that a session resumed from `/order/confirm` arrives with the `from` its first visit had. No code change.
