# #253 — daily cap on chat turns (batch 3, slice 1)

Branch `claude/253-chat-quota`, from main `5322cfb`. No schema change, no
migration: `npm run db:generate` must print "No schema changes".

## Problem

`sendChatMessage` (`src/app/design/actions.ts`) makes one Claude Sonnet call
per turn for any session, anonymous guests included, with no cap. Its only
caller is `src/app/design/design-client.tsx` (the `/design?id=` thread).

## Owner decisions (binding, batch-3 plan "Answers" item 10)

- Guests may chat.
- Count chat turns per identity and per IP, per UTC day, in
  `generation_usage` under their own bucket prefixes: `chat:user:<id>` and
  `chat:ip:<addr>`.
- Default daily caps: guest 24, signed-in user 150, IP 60, from env
  `GUEST_CHAT_DAILY_CAP`, `USER_CHAT_DAILY_CAP`, `IP_CHAT_DAILY_CAP`.
- Over the cap: refuse with no Anthropic call and no chat rows written. The
  user sees a plain refusal (persona C copy).

## Design

Same mechanism as `consumeGenerationQuota`: one atomic
`INSERT … ON CONFLICT(bucket, day) DO UPDATE SET count = count + 1 RETURNING
count` per bucket, then a decision on the post-increment count. Each bump is a
single statement, so two concurrent turns at cap − 1 get counts cap and
cap + 1 and exactly one is admitted. No interactive transaction is needed.

Controller rulings that shape the design (details and costs in the ledger):

1. The chat cap is enforced whether or not `GUEST_FUNNEL_ENABLED` is on (the
   Anthropic cost exists for any session).
2. The IP dimension applies to guest turns only. Signed-in turns bump and
   check only `chat:user:<id>`. Otherwise a signed-in user on any IP would
   hit the IP cap (60) long before the user cap (150), and the owner's
   signed-in cap would never be reachable.
3. The identity bucket is checked first; when it is already over its cap the
   IP bucket is not bumped, so one guest spamming refused turns does not use
   up the network's allowance for other guests.
4. A turn whose Anthropic call throws gives its unit back (identity, plus IP
   for a guest), best-effort, on the day it was spent.
5. Order inside `sendChatMessage`: session → `findOwnedDesign` (throws on a
   foreign design) → `assertConversationOpen` when the design exists → chat
   quota → create the design row if new → Anthropic → persist. A refused turn
   on a never-seen design id leaves no design row (same rule as #197 for
   generate) and burns no unit on a foreign or closed conversation.

## Task 1 — quota functions in `src/lib/generation-quota.ts`

Add, next to the generation functions and without changing their behaviour:

- `GUEST_CHAT_DAILY_CAP` (default 24), `USER_CHAT_DAILY_CAP` (150),
  `IP_CHAT_DAILY_CAP` (60), read like the `*_GEN_DAILY_CAP` constants.
- Bucket builders so the prefixes live in one place:
  `chatUserBucket(id) = "chat:user:" + id`, `chatIpBucket(addr) =
  "chat:ip:" + addr`.
- `consumeChatQuota({ userId, isAnonymous, ip, now?, db? })` →
  `QuotaResult` (`{ allowed, reason?: "identity" | "ip" }`). Rulings 1–3.
- `refundChatQuota({ userId, isAnonymous, ip, day, db? })`: decrement the
  same buckets the consume bumped, floored at 0 (reuse `unbump`).
- Update the module header comment to describe both families and state that
  generation functions touch only `user:`/`ip:` buckets and chat functions
  only `chat:` buckets.

Acceptance criteria:

- The generation functions' SQL and behaviour are unchanged.
- No function reads or writes a bucket outside its own family.
- Exact-match `bucket = ?` everywhere; no `LIKE` on bucket.

Tests (new `src/lib/__tests__/chat-quota.integration.test.ts`, real
in-memory libSQL via `createTestDb`):

- Guest: turns 1..24 allowed, turn 25 refused with reason `identity`.
- Signed-in: turns 1..150 allowed, turn 151 refused with reason `identity`,
  and a signed-in user's turns write no `chat:ip:` row.
- IP: 60 guest turns spread over three guest identities on one IP are
  allowed, the 61st refused with reason `ip`; a signed-in user on that IP is
  still allowed.
- A guest refused on identity does not bump `chat:ip:`.
- Isolation, both directions: a user at the generation cap (both `user:` and
  `ip:` buckets) is still allowed chat; a user at the chat cap is still
  allowed generation; chat turns leave `user:`/`ip:` rows untouched and
  generation leaves `chat:` rows untouched; `refundGenerationQuota` leaves
  `chat:` rows untouched and `refundChatQuota` leaves `user:`/`ip:` rows
  untouched.
- Concurrency: with the identity bucket seeded at cap − 1, two concurrent
  `consumeChatQuota` calls (`Promise.all`) admit exactly one; same for the
  IP bucket.
- Enforced with `GUEST_FUNNEL_ENABLED` unset.
- `refundChatQuota` floors at 0 and targets the passed day.
